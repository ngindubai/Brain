## Story 1: Researchers start building the failure-analysis stack for agents, all in one day

**Source:** arXiv cs.AI daily listing, 13 September 2026 | http://export.arxiv.org/rss/cs.AI
**Related vault notes:** [[Agent Org]]

Today's arXiv cs.AI submissions include an unusual concentration of papers aimed at one problem: agents fail in ways nobody is systematically tracking yet. "The Agent Incident Registry: Toward Preventing Repeated AI Agent Failures" (arxiv.org/abs/2609.11030) proposes a shared catalogue of agent incidents with causal roles and outcomes — essentially a CVE database for agent screw-ups. Alongside it, "Defining AI Agents: A Compendium of Criteria, Metrics, and Benchmarks" (arxiv.org/abs/2609.11018) tries to standardise what "agent" even means across five evaluation dimensions, and "Benchmark Radar" (arxiv.org/abs/2609.11115) builds a living search index over agentic and tool-use benchmarks specifically because the current benchmark landscape is too fragmented to compare claims. A fourth paper, "Finishing the Task Is Not Enough: Evaluating Agent Resilience and Considerate Participation under Accumulating Challenge" (arxiv.org/abs/2609.10724), argues that task completion is the wrong metric entirely and proposes scoring agents on how gracefully they degrade under repeated friction.

None of this is a lab announcement, but the clustering matters. It lands in the same week security researchers disclosed sandbox escapes across Claude Code, Codex and Cursor, and days after GreyNoise documented hundreds of AI agents autonomously compromising 395 organisations through PaperCut flaws (both already tracked in open loops below). Academia is visibly racing to build the measurement and incident-tracking infrastructure that the labs shipping these agents did not build first. For anyone designing an agent org — including this one — the practical takeaway is the same one keeps surfacing: nobody has a mature failure taxonomy yet, so internal incident logging and degradation testing has to be built in-house rather than borrowed off the shelf.

## Story 2: Enterprise agent memory gets its own research push

**Source:** arXiv cs.AI daily listing, 13 September 2026 | https://arxiv.org/abs/2609.11060
**Related vault notes:** [[Agent Org]]

"Grounding Agent Memory: Environment-Probing Curation for Enterprise Agents" tackles a narrower but practically urgent problem: long-horizon enterprise agents accumulate memory across sessions, and most of it is stale, wrong, or ungrounded in the actual state of the systems they operate in. The paper proposes actively probing the environment to curate what an agent remembers rather than passively logging everything. This is a direct answer to a complaint that keeps surfacing in production agent deployments — agents that "remember" a CRM field name or an API contract that changed three weeks ago and confidently act on stale context. Worth flagging for any Orwell agent-department design that leans on persistent memory rather than re-deriving state each run.
