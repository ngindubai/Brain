## Story 1: Google forces Local Inventory Ads into every eligible Shopping campaign today

**Source:** PPC Land / Google Ads Developer Blog | https://ads-developers.googleblog.com/2026/07/enabling-local-inventory-ads-by-default.html and https://ppc.land/google-forces-local-inventory-ads-on-all-shopping-campaigns-august-31/
**Related vault notes:** [[SEO Portfolio]]

Google confirmed on 28 July that from today, 31 August, Local Inventory Ads (LIA) become the default state for every Shopping campaign in an account where the linked Merchant Center has the LIA add-on enabled. The change removes the "Local products" toggle from campaign settings entirely. Advertisers previously able to keep online and local inventory in separate, deliberately configured campaigns now have that decision made for them at the account level, and must instead manage the split using an Inventory filter (Channel = Local or Channel = Online) bolted onto existing campaigns.

The mechanics matter because this is not additive, it is structural. Any account with a Business Profile carrying verified store locations and a local product feed in Merchant Center will now serve local inventory ads alongside online Shopping ads automatically, which changes budget pacing and conversion attribution across every affected campaign the moment the rollout hits. Advertisers who wanted online-only Shopping campaigns for legitimate reasons (fulfilment capacity, margin protection on certain SKUs, geographic exclusions) lose that lever unless they rebuild it manually through the new filter.

For accounts with no local feed and no verified store locations, Google says the change has no practical effect. That is the relevant line for Orwell: none of the [[SEO Portfolio]] properties (pet transport, funeral repatriation, close protection hire, global bus hire, pest control) or the [[Comparison Network]] sites run physical retail inventory or Shopping campaigns, so this deadline passes without action on the current asset base. The one place it is worth a mental flag is any future KlientFlo-type client build for a business with physical retail locations, where this now-default behaviour would need to be audited into the PPC setup from day one rather than assumed away.

The broader signal is consistent with everything else Google has done to Shopping and Search campaigns this year: fewer manual toggles, more automated blending of formats, and migration deadlines advertisers are notified of by email rather than given a genuine choice on. It sits alongside the AI Max auto-upgrade (open loop below) as part of the same pattern.

## Story 2: Bing Webmaster Tools retires its legacy SOAP/POX API today

**Source:** Search Engine Roundtable / Bing Webmaster Tools Help | https://www.seroundtable.com/bing-webmaster-tools-soap-pox-apis-retire-41805.html
**Related vault notes:** none

Microsoft's deadline to retire the SOAP and POX protocol versions of the Bing Webmaster Tools API lands today, 31 August. After today, requests to those legacy endpoints stop being served; only the JSON/HTTP (REST) version continues to work. Microsoft's own guidance frames this as a low-friction migration: every API method remains available with identical functionality over REST, API keys carry over without reissue, and quotas, rate limits and permissions are unchanged.

This is not a breaking-news story so much as an infrastructure hygiene deadline, but it belongs in the sweep because it is exactly the kind of thing that silently breaks an automation nobody has looked at in a year. If anything on the [[SEO Portfolio]] or [[Comparison Network]] side has a script, plugin, or third-party tool submitting sitemaps or pulling crawl stats from Bing via the old SOAP or POX calls, that integration stops working from today with no further warning, since Microsoft has been signalling this for months. Worth a five-minute check alongside the overdue Cloudflare portfolio audit: confirm nothing in the stack still calls the old Bing endpoints.

Bing Webmaster Tools remains a minority channel next to Google for a lead-gen portfolio this size, so the ceiling on the downside here is low. But "low downside, zero-cost check" is exactly the kind of item that belongs on a maintenance list rather than being left to surface as a mystery indexing gap three months from now.

## Story 3: Ahrefs Brand Radar's old-volume toggle disappears today

**Source:** Ahrefs (via X/web search corroboration) | https://x.com/ahrefs/status/2085287428550496326
**Related vault notes:** none

Flagged yesterday as a forward deadline, this is now live: Ahrefs has removed the temporary toggle that let Brand Radar users switch back to plain Google search volume. From today, every Brand Radar report runs exclusively on Ahrefs' AI-adjusted volume metric, calculated as a prompt's parent keyword's Google volume multiplied by a platform-specific usage ratio (how much that platform is used relative to Google).

The practical consequence: any brand-visibility tracking done in Brand Radar before today used one volume basis, anything pulled from today onward uses a different one. Trend lines that cross this date are not a clean before/after comparison unless Ahrefs backfilled historical data on the new methodology, which the available sources do not confirm either way. This is a short item precisely because there is nothing new to analyse beyond confirming the switch actually happened on schedule; it slots into the existing Semrush/Ahrefs tooling-gap open loop rather than standing alone as a fresh development.
